# 第一個可行性實驗：從獨立專案到可追查路徑

依據：[契約 v0.2](AGENT-DEBUG-CONTRACT.md)、[驗收矩陣](AGENT-DEBUG-ACCEPTANCE.md)。狀態：計畫，尚未執行；本文件不是現成 CLI 或已驗證工具。

## 要消除的未知

Agent 能否在一個原本沒有本 repo 埋點的 Lexical 0.18.0 專案中，只靠專案分析與集中生成的觀測 patch，取得足以支持下一個實驗的來源/執行關係，並讓人從摘要直接定位證據？

第一個候選路徑是「listener 執行 → 發起 editor.update → 後續更新」。它是待驗證的捕捉目標，不預設它就是公司瓶頸，也不預設 update callback 返回等於 DOM/React/paint 完成。

## 進入條件與準備

在已授權的獨立專案進行；若先用受控案例，保留其原有架構，不複製 demo collector。Evaluator 準備 neutral case 與答案，agent 不取得 oracle。人完成登入/一次性初始化後記 ready 時點。

先明訂：案例、必要首屏內容、重現與 reset、tool/版本/模型、scope、並行上限、探測排程、錄製上限、setup/cleanup 超時及停止方式。不得在開始計時前替框架組掃描專案或建好專用索引。環境未 ready 時可報 setup-blocked，但記錄準備成本，不能無限準備。

## 30 分鐘內的工作

以下是可調整的初始分配建議，只有總計 30 分鐘是已確認硬限制：

| 時段 | 目標與出口 |
|---|---|
| 0–7 分鐘 | 建立基準重現與相關來源子圖；若不能重現，交付差異與缺口，不假裝進入歸因 |
| 7–15 分鐘 | 選最少足夠的觀測位置，生成 patch；確認型別/build/相關行為與來源映射 |
| 15–24 分鐘 | 錄製並對齊原始證據，分開 captured 關係與推論；查最昂貴或有區辨力的一條路徑 |
| 24–30 分鐘 | 驗證導航，交付可否證下一實驗；有餘裕才執行單一介入，不為追求修復拖過期限 |

如果既有 CPU trace 已足夠，不為了展示自動埋點而加探針。反之，若來源與 async 關係缺失，先補最能區分解釋的邊界，不追求全圖。

## 兩個必要能力檢查

**證據導航：**從一筆摘要選取事件，使用實際可用的 Chrome/Perfetto 接合，定位同一份 trace 的同一事件或精確時間區間；再開啟正確版本來源。保留導航映射及實際操作證據。不能只輸出時間字串要求人手動搜尋，也不假定某個未測試的 deep link/SDK 存在。

**可操作量測：**外部程序在預定時點送輸入/捲動，記 dispatch 與預期可見效果。用已知延遲案例驗證方法能區分 handler 已執行但畫面尚未回應。時鐘/可見效果精度不足時標 unverified，不能把兩次 rAF 代入 100 ms 門檻。

兩者若無法在本案預算內完成，可以交付支持的部分與缺口；不得因此把未完成項目從驗收刪掉。後續另立 capability spike，仍明列範圍與預算。

## 必須留下的結果

1. case/capability manifest、來源與 patch 身分、完整成本與停止原因。
2. project 子圖、probe plan、實際 patch、原始 run/trace；缺口/失敗也保留。
3. 有界摘要：observed/inferred/unknown、可追查 ID、來源與導航入口。
4. 一個實驗卡：介入/控制、功能要求、結果分支，以及支持/削弱/無法區分的判定。
5. 對照者能重跑的步驟；需要人工確認的部分明列。

## 支持、推翻與停止

- 支持可行性：獨立專案能集中生成觀測；捕捉的邊可被原始執行證據支持；摘要導航成功；下一實驗可在既有環境執行。
- 削弱此設計：仍需要人逐一修改每個 plugin；來源/時鐘無法對齊；觀測造成行為改變或主要成本轉移；導航只能靠人工比對。記錄具體失敗機制，先修接合邊界。
- 停止：到 deadline、無法重現、必要權限/資料/工具缺少、或產物不可信。保留證據，輸出 blocked/inconclusive 與下一個最小驗證；不延伸成 replay、通用 SDK 或大型 UI 開發。

此 spike 通過只支持繼續實作必要 enforcement。之後才執行獨立 session 的自由調查對照與真實案例驗收，不能把一個受控成功案例當成框架已優於現有工具。
