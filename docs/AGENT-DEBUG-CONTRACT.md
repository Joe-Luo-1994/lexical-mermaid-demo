# Agent Debug 調查契約 v0.2

日期：2026-11-11。狀態：**使用者需求基線已確認；下列 enforcement 是待實作、待驗證的工程設計。** 目前有規格與合成 DX 設計原型，沒有交付通用 collector、runner 或新的 OpenCode 工具。

本文件是新方向的需求來源。[驗收矩陣](AGENT-DEBUG-ACCEPTANCE.md) 定義如何否證它，[第一個可行性實驗](AGENT-DEBUG-SPIKE.md) 定義下一步。舊工作台與 Mermaid/Pele 比較是參考工具及回歸素材，通過其測試不代表本契約通過。

## 1. 產品任務與已確認決策

讓內部 agent 在已授權的既有專案中，依據一個具體問題，掃描相關程式、生成專案當前版本所需的觀測與實驗，交付可追查的執行路徑及下一步。穩定的核心是調查規約與證據協定；adapter、探針與部分視圖可由 agent 在 worktree 中生成。不是要求單一 library 預先適配所有專案。

| ID | 已確認需求 |
|---|---|
| REQ-01 | 網站已開啟且使用者已登入，點進一份尚未顯示的文件；顯示過程主執行緒阻塞約 3 秒。網路傳輸已由使用者排除為本案來源。 |
| REQ-02 | Lexical 0.18.0；OpenCode 2.2.5 Web、server 在本機；公司內網。框架從 public repo 的 main 交付。 |
| REQ-03 | 公司 agent 可啟動專案及操作 Playwright/Chrome DevTools；必要的登入或一次性初始化由人完成。實際能力仍需 preflight 查核。 |
| REQ-04 | 已核准範圍內，可在隔離 worktree 自動加觀測、製作候選修復與測試；合併由人決定。不代表雲端 session 可讀公司檔案。 |
| REQ-05 | 每案最多 30 分鐘，從環境可啟動且登入完成後開始。掃描、索引、重現、埋點、後續建置、分析及實驗均計入。 |
| REQ-06 | 優先交付可信執行路徑與一個有判別力的下一實驗；不要求每案修好。 |
| REQ-07 | 首屏內容完整且可輸入、捲動可算恢復；畫面外內容可延後，但必須驗證捲入時的完整性與回應。 |
| REQ-08 | 輸入與捲動從瀏覽器外送出，到預期可見回應的延遲，先以不超過 100 ms 為工程門檻。不是整份文件要在 100 ms 載入。 |
| REQ-09 | 可沿用 Chrome DevTools/Perfetto；摘要須能定位同一事件、時間區間與來源，不依靠人手工比對。第一版不要求自製統一 UI。 |
| REQ-10 | 如實記錄 token 與模型費用，暫不設額外硬上限；取不到 usage 或價格時記 unknown，不能寫成 0。 |
| REQ-11 | 受控盲測與真實專案分開驗收。包含已知瓶頸、正常昂貴工作、時間相近但無因果關係的事件。 |
| REQ-12 | 對照相同案例、模型、基礎工具、預算與並行資源上限的自由調查 agent，評估正確定位、時間、token、人工介入。 |
| REQ-13 | DX 必須支援看懂、查證、續接：呈現判斷/支持/未知/下一實驗，缺能力可定位，換人或 agent 能使用案例產物接續。具體設計見 [DX 設計](AGENT-DEBUG-DX.md)，互動原型不等於可用性或 runtime 已驗證。 |

Pele 已在公司試用且使用者回報效能良好；實際 Pele/React/browser 版本、source map 與公司專案結構仍未知。不得套用公開 demo 的版本或數據。

## 2. 本案的量測與成功定義

### 操作與時間

- `operationStart`：網站已開啟後，外部自動化送出指定開啟文件動作。另記瀏覽器接收/處理時間，不把等待頁面可操作後才送出的動作當作原本觸發時間。
- `firstViewportComplete`：案例事先列出的首屏必要文字、表格、圖表與控制皆完成；骨架、空殼、佔位不算。案例的必要內容清單與 viewport 在比較前固定。
- `interactionResponse`：外部送出輸入/捲動到預期可見效果的延遲。handler 執行、DOM 變更、React commit 或兩次 rAF 都不能單獨證明可見回應。
- `recoveryObservation`：首屏完整，且事先指定的輸入與捲動探測各自滿足 100 ms。記錄探測時點與前一個失敗探測；離散探測只能給恢復區間/上界，不聲稱精確找到最早恢復時刻。
- `deferredContentResponse`：若延後畫面外內容，依固定捲動路徑驗證內容完整、回應及新增阻塞，不能只驗收首屏。

所有指定探測逐筆保留；不得用中位數掩蓋超過 100 ms 的探測。符合本次探測不代表永遠滿足門檻。首屏完成與總恢復時間另列，不把 100 ms 當成載入總時間預算。

跨 runner、browser trace、頁面與 Worker 時鐘，須記錄對齊方法與誤差界線。若延遲的不確定範圍跨過 100 ms，該探測是 inconclusive；沒有可見效果的可信量測，只能報 handler/DOM 代理值。不得將缺測算通過。

網路不是本案主要調查方向，但仍保存資料/快取就緒條件，避免 A/B 的網路差異污染結果。網站首次啟動、首次下載 library 與本案「已開啟網站後進文件」不是相同條件。

### 四個獨立判定

1. **契約合格**：範圍、身分、證據、限制與預算正確處理；誠實的 blocked/inconclusive 可合格。
2. **診斷有用**：有證據的執行路徑，且下一實驗的不同結果確實會改變判斷或行動。
3. **修復成立**：比較契約、功能檢查、事前判定規則與效能證據支持該修復。
4. **框架有效**：在保留案例的對照中顯示可重現的可靠性/效率收益，不能由單次成功推定。

30 分鐘後只有不足證據，不能計入診斷成功；定位但尚未修好可以達到本版主要目標。沒有定義最小有用改善與取樣規則時，不授予「修復成立」。第一版未承諾特定載入秒數或改善百分比。

## 3. Invariants 與預定 enforcement

以下每項均須實作後經驗收才能標為 enforced；寫在 prompt 裡只算指引。

| ID | 不變條件 | 預定強制檢查與失敗行為 |
|---|---|---|
| INV-01 | 範圍有界：指定專案、操作、案例、讀寫位置與資料流向 | preflight/runner 驗證 scope manifest；未授權路徑不操作。資料留在核准環境，不因 public 工具 repo 而公開公司內容。 |
| INV-02 | 證據綁定實際版本 | 保存 commit、既有 diff、觀測/修復 patch hash、相關來源指紋、build、lockfile、browser/viewport/字型與案例身分；來源變更後重新判斷受影響索引/探針，不能只因 worktree 名稱相同就重用。 |
| INV-03 | 結論可追查 | observation 必須引用本次真實 run/event/source；validator 拒絕失效、重複或跨錯誤 run 的引用。原始資料保留，摘要可重建。 |
| INV-04 | 關係強度不得高於證據 | 邊分 static-call、captured-call、captured-schedule、temporal-association、hypothesis；各有必填來源。沒有捕捉排程就不能填因果 parent；時間相近不升級為觸發關係。 |
| INV-05 | 缺觀測不得推為沒發生 | 保存探針安裝/啟用、預期觀測邊界、遺失事件數與未知區域；無覆蓋依據不得宣稱某 plugin 未執行。覆蓋率分母未知時不得顯示百分比。 |
| INV-06 | 每個探針有決策用途 | probe plan 必填要消除的未知、位置、可能結果/下一步、成本與上限。無具體用途不執行；初期短 profiling 可用於縮小未知區間，無須捏造假設。 |
| INV-07 | 觀測不得無聲改變行為 | 範圍 diff、型別/build、相關行為與 cleanup 檢查；觀測若改變 this/例外/回傳/排程語意或造成失敗，該 run 不得當正常行為證據。測試僅支持已測情境，不是完整等價證明。 |
| INV-08 | 觀測成本可見且有界 | 錄製前明訂時間、事件/位元組/stack 深度上限；超限明記遺失或停止。未校準開銷的詳細 trace 可診斷，不可混入一般效能驗收。重疊/包含的 span 不可直接相加當 CPU 時間。 |
| INV-09 | 比較須有事前契約 | 固定功能要求、案例、環境、量測終點與取樣規則，列出刻意介入及來源差異；不相容時保留資料但拒絕改善彙總。不能透過少畫內容、換掉必要功能或轉移卡頓通過。 |
| INV-10 | 不挑樣本、不改答案門檻 | runner 記錄每次嘗試、停止/失敗/排除理由；不得重用 sample ID 或隱藏慢值。事後改閾值或測試須建立新實驗修訂並揭露探索性結果。 |
| INV-11 | 調查期限不能被繞過 | browser 外 controller 從 ready/authenticated 時點計 1,800 秒；所有子任務共用 deadline。截止不啟動新調查，停止自己擁有的工作並保留證據；清理另有事前上限且計入總成本，不藉清理繼續分析。 |
| INV-12 | Agent 不能自行放寬驗收換取通過 | validator/基準測試/判定規則 pin 版本與指紋；候選修復不得同時偷偷改 acceptance oracle。規則變更是新版本，需獨立檢視。 |
| INV-13 | 人與 agent 看同一份證據 | 摘要、時間定位、關係子圖與來源導航共用 run/event/source identity。UI 聚合保留 drill-down 與省略數；轉換格式不得丟失引用或偽裝成既有 recording。 |
| INV-14 | 狀態與不確定性不可在摘要、視圖或交接中消失 | execution、verdict、freshness、capability 分開；摘要/匯出同一資料投影，保留反例、缺口與截斷資訊。失效來源不能靜默換成近似來源。 |
| INV-15 | 調查可中斷並可信續接 | checkpoint 保存已做/失敗嘗試、原始證據引用、下一實驗、來源指紋、deadline 與累積成本；恢復前查核適用性，禁止續接重設預算。 |

### Enforcement 的可信界線

- Schema/ref 檢查只證明格式，不證明執行真實或因果。錄製來源、生成 patch、可重跑案例與獨立 trace/實驗仍需查核。
- 執行限制只約束經 runner 的操作。OpenCode 若仍有任意 shell，就不能聲稱全程沙箱；宿主檔案/工具權限是另需查核的能力。
- Agent 產生的 probe plan、來源歸因、ready predicate 都是待驗證產物；不能用同一 agent 的自評當作通過證據。
- 不要求知道每個 plugin 的名字。可顯示已確認的 registration/source location；名稱或 owner 無法解析就明列 unresolved。

## 4. 調查產物與導航契約

下列是邏輯產物，檔名是設計提案，**尚無 CLI/工具可執行此協定**：

| 產物 | 必須回答 |
|---|---|
| case manifest | 操作、必要內容、環境、scope、預算、資料條件、探測排程與驗收版本是什麼？ |
| capability manifest | 哪些工具/版本、source map、時鐘對齊、cost meter、導航功能實際測過？哪些未知？ |
| project map + probe plan | 此問題的相關來源/候選路徑；為何觀測、如何生成/移除、什麼結果改變下一步？ |
| patches + raw runs | 當時實際跑了哪份程式、探針與操作？包含失敗、遺失與取消。 |
| findings + evidence index | 觀測/推論/未知、證據 ID、來源版本、可直接定位的時間與檔案引用。 |
| experiment + decision | 唯一或明確列出的介入、固定條件、預測、結果及支持/削弱/無法區分的判定。 |
| cost + exit record | wall time、setup/人工等待/清理、各模型 usage/費用、工具呼叫與人工介入；截止與結論分開。 |

Agent 先讀有界摘要，按 ID 取必要事件/子圖/stack。可建立完整索引，但不把整庫內容塞入上下文或人類畫面。過濾須可回到原始證據，不能用「降噪」刪除反例。

人類可使用現成 viewer，但必須從摘要導航到對應 trace 的事件/時間範圍及正確版本來源。只有「把 trace 打開，搜尋這個時間」不合格。若 Chrome/Perfetto 不支援需要的定位，先驗證最小接合；不能假裝已有 deep link API。第一個 spike 必須驗證此處。

## 5. 範圍、非目標與待實測項目

第一版不處理：通用 editor/所有 Lexical 版本、所有語言與工具適配、完整動態呼叫圖、確定性 browser replay、生產常駐監控、一般網路/後端診斷、自動合併/部署、每案唯一根因保證、自製大型 UI 平台。

現有 schemaVersion 1 recording、Chrome trace、renderer-comparison JSON 與未來 investigation artifacts 是不同格式。既有 editor-evidence plugin 不會因規格發布就能讀新格式。

下列由第一個 spike 或公司 preflight 取得，不要求使用者憑記憶填寫，也不得默認已支援：

- 公司路徑、讀改範圍及允許的模型資料流向；沿用 session 已授權資訊，不重複要求。
- React/Pele/browser/tool 實際版本、source maps、啟動與重現命令。
- 可見回應的量測方式、跨時鐘誤差與 100 ms 門檻的可判定性。
- 工具的事件/時間/來源導航、觀測開銷與合理錄製上限。
- setup/cleanup 超時與隔離方式、agent 並行資源上限、成本資料可取得性。
- 具體首屏內容、操作 reset/快取策略、代表性探測時點/捲動路徑、取樣規則與最小有用改善。

這些必須在相應執行/比較前落成 manifest。缺少項目可阻擋相關聲稱或輸出 blocked；不能用未定參數偷偷擴張第一版。新增平台、介面或優化策略需記錄觸發證據與範圍變更。

## 6. DX 契約與第一版設計

[DX 設計](AGENT-DEBUG-DX.md) 定義第一屏、事件 inspector、實驗與交接流程，以及兩輪迭代與獨立 review。第一版沿用既有 viewer；不將大型自製 UI 列為必要交付。OpenCode 2.2.5 Web 的內嵌/雙向同步須實測，不假定 API。

DX 的硬性正確性包含引用一致、版本失效處理、反證可見與預算續接；理解成本、查證時間及接續效率另由人類任務與 fresh-agent 對照驗證。外觀與鍵盤/窄畫面是產品品質檢查，不可代替診斷準確率。以相同成功層級比較成本，token 下降但錯誤歸因上升不算改善。

原型內的事件、時間、來源與交接格式均為合成示意；不能拿來通過 AT-13/14/15 或聲稱已完成公司診斷。正式接合以第一個 runtime spike 為準。
