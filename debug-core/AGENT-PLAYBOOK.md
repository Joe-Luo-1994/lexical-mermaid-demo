# 交給內部 agent 的調查規約

適用：Lexical 0.18.0，網站已開啟後進入文件，主執行緒卡頓；OpenCode 2.2.5 Web/server 本機。使用者已排除網路傳輸為本案主要來源。工具 repo 的 main 是唯一交付分支。

## 可貼入 OpenCode 的起始任務

```text
請使用 <tool-repo>/debug-core 的既有核心，調查 <已授權專案/worktree> 的 <可重現文件操作>。
先讀 debug-core/README.md、AGENT-PLAYBOOK.md、FORMAT.md 與 VALIDATION.md。
沿用本 session 已授權的資料與修改範圍；不要重複詢問已知資訊。
必要登入/一次性初始化由我完成。環境 ready 後立即 init 案例；掃描、索引、生成探針、後續建置與所有子任務共用原本 30 分鐘。
可在隔離 worktree 生成觀測、候選修復並測試，合併由人決定。
優先交付有證據的執行路徑與能區分解釋的下一實驗；缺少量測能力就明列，不能拿 DOM/兩次 rAF 代替可見回應。
以 CLI 或唯讀 editor-debug-case 查詢小摘要，按 ID 深入。不要修改核心驗收來讓案例通過。
最後交付本機 viewer 入口、case 路徑、支持/未知/失敗紀錄、下一實驗、剩餘預算與成本缺值。
```

## 核心與生成物的責任界線

| 固定核心 | 本案 agent 生成並驗證 |
|---|---|
| case/attempt 身分、原 deadline、版本與引用檢查 | 啟動、重現/reset、文件與必要內容 |
| 有界資料、失敗/中斷記錄、未知狀態 | 問題相關來源子圖，選擇觀測邊界 |
| raw/source snapshot 導航與唯讀 query | 探針/adapter patch、語意與 cleanup 檢查 |
| 事件關係類型、不升級假設、誠實能力標示 | findings、反證與限制、下一實驗、候選修復 |

核心接受 capture 只證明結構與引用符合其檢查。Agent 仍須檢查探針 this/回傳/例外/排程/cleanup、來源映射、量測開銷、資料完整性。找得到某條呼叫路徑不代表該路徑造成卡頓；看到慢 callback 不代表應刪除必要功能。

## 執行順序

1. **開始計時**：初始化 case 後才掃描來源。確認 root 與當前修改，不 reset/clean。若使用者尚未提供公司路徑，停在這個缺口，不自行搜尋公司資料。
2. **先重現，後加觀測**：既有 CPU trace 若能回答問題就使用；否則生成最少探針，plan 說明不同結果如何改變下一步。各種圖/表的完整性條件在比較前固定。
3. **讓生成物可審查**：保存相對來源與 adapter/build 身分；diff/build/相關行為通過後錄製。Adapter 不是 sandbox，只執行已核准程式。若新增檔案，必要時保留 patch/版本資訊以重建原狀。
4. **取得一條可信路徑**：查來源快照、rawRef、關係類型與遺失資訊。捕捉不到 async parent 就保留未知，不補上想像中的呼叫鏈。
5. **提出／執行介入**：在原 deadline 有餘裕才跑候選修復；功能、快取、viewport、採樣與量測終點事先固定。現有核心不授予 improvement-validated，結果交由獨立驗收。
6. **保存與交接**：退出原因與判斷分開記。fresh agent 先查 case、失效來源、已做實驗與剩餘時間，不把新 session 當成重設預算。超時後只交接；若正式新開調查須揭露新 attempt 與歷史成本。

並行 agent 可分工靜態查找或 review；所有成本合併，效能量測不要並行互相搶 CPU。Reviewer 檢查證據與反例，不能只重述調查 agent 的結論。

## 不確定時問什麼

只問會阻擋當前步驟的問題：未給定的公司讀改範圍、無法自行取得的重現操作、尚未完成的人為登入、不可推定的必要功能。工具版本、source map、plugin 來源、是否可錄製等，先以已允許工具查證，不請使用者憑記憶回答。

## 合格交付

不要只說測試通過。必須有人能從摘要找到同一 run/event/source；下一個 agent 能知道哪項解釋已被削弱、什麼尚未測，以及哪個結果會改變下一步。真實可見回應量測、公司診斷、盲測及效率對照仍分開驗收。
